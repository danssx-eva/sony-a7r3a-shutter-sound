# 逆向方法

从"现象"到"地址"的流程是固定的五步：定层、只读确认、找调用链、固化特征、落盘并冷启动验证。每一步都有判断标准，不满足就不往下走。

## 为什么先讲流程

因为这个项目里最贵的教训不是某个地址找不到，而是**把"没反应"的原因猜错了方向**。

三天里的真实循环是：写代码、上机、没反应、猜原因、再写。复盘时发现几乎每一次失败都不是代码写错，而是改动没有到达它该到的地方。把"验证到哪一步了"当成流程的一部分，比提高写代码的能力更省时间。

## 第一步：把现象定到一层

先不碰相机，先看只读信息。这一步几乎零风险，而且能避免大部分"地址错"。

```bash
# 相机状态总览：库 SHA、钩子字节、uptime、分区、ext2 超级块
python tools/camera/a7r3a_status.py

# 只读侦察：内核模块、驱动参数、dmesg、块设备、工具清单
python tools/camera/a7r3a_recon_kernel.py
```

手工要看的东西：

```sh
busybox cat /proc/155/maps      # 模块基址
busybox ls -l /proc/155/fd      # 进程都在碰哪些设备
busybox cat /proc/modules       # emmc.ko 还是 nand.ko
busybox ls /dev                 # 有没有音频节点
```

判断标准：现象落在 AP 还是 CP。位置决定后面所有动作，判断错了会一直在错误的模块里找。

这一步还要把能读到的都存下来，这是唯一的恢复素材：

```text
/usr/lib/libObj.so              记下 SHA256（本机 f1351204…）
/usr/lib/viewUnified2.so
/usr/lib/CautionConfig.so
/usr/share/avsystemsound/*.bin  以及 beeplist.txt
/proc/155/maps                  全部模块基址
/proc/mounts                    分区与挂载
```

用 `tools/camera/a7r3a_watch_pull.py` 拉模块，用 `tools/camera/a7r3a_status.py` 记状态。这一步不做，后面全是赌博。

例子：电子快门下不响。AP 侧的 `M_BEEP::Execute` 是全部提示音的入口，看起来是理想目标。但 `/dev` 里没有音频设备，说明声音由 CP 产生，AP 只是请求方。于是问题从"钩哪个播放函数"变成"请求发没发出去、什么时候发"。

## 第二步：装探针确认路径是否被走到

在改任何东西之前，先让相机自己告诉你它有没有走到那条路径。

探针优先用**内存计数器**，不要用写文件：

```sh
# 读计数器（只读）
python tools/probes/read_probe.py --wait 10

# 需要归零时（这一步会写内存，不是只读）
python tools/probes/read_probe.py --reset
```

写文件探针会因为 `open` 失败、会话降级、通道降级而丢证据。内存计数器零 syscall、零阻塞，
读回走 `/proc/<pid>/mem`，这条通道实测最稳。

**计数器必须放在可写段。** `libObj.so` 的第一个 `PT_LOAD` 是 `r-xp`（只读可执行），
往里面 `str` 会触发权限异常，载荷当场崩。可用的可写位置是 `libosal_uipc.so` 的
`.bss` 尾部，运行期 `0x0405EFE0` 一带（该段在 maps 里是 `rw-p`）。

> 这一条踩过：早期把计数器放在 `libObj` 的 `fileVA 0x194A18`，看起来是载荷附近的空档，
> 实际是只读页。载荷里第一次写就崩，读回的计数器永远是 0，于是误判"这条路径没被走到"。

`tools/probes/` 里现在只有 `read_probe.py`（读那个可写计数器）。早期还有几个观察型钩子
（`probe_setvalue.py` 记 `setValueToModel` 参数、`probe_bkup.py` 记 `Bkup_Write` 的 BKID、
`menu_probe.py` 读菜单节点），都是一次性脚本，已随其他一次性脚本一起下架。

判断标准：计数器有增量，才说明这条路径在运行期被走到。没有增量之前，任何"函数里明明有发声分支"的推理都不算证据。

## 第三步：找调用链

从现象所在的函数往上或往下追，直到拿到一个稳定的地址。

下面命令假设 dump 在 `logs/watch/usr_lib_libObj.so`；没有的话，把 `--file` 换成你的备份路径，例如 `backup/<时间戳>/usr_lib_libObj.so`。

```bash
# 谁调用了某个地址（BL / B.W / BLX 和字面量引用），并给出所属函数
python tools/analysis/who_calls.py --file logs/watch/usr_lib_libObj.so --target 0x0FF7B8

# 把 PLT 存根按 .rel.plt 顺序解回动态符号
python tools/analysis/plt_map.py --file logs/watch/usr_lib_libObj.so

# 字符串引用：ADR / LDR literal 两种寻址都找
python tools/analysis/find_string_refs.py --file logs/watch/usr_lib_libObj.so

# 任意 link-time 虚拟地址的 Thumb 代码引用
python tools/analysis/xref_address.py --file logs/watch/usr_lib_libObj.so 0x1948D8
```

反汇编在 Ghidra 里做，但**地址要换算**：默认 imageBase 是 `0x10000`，所以 `fileVA = Ghidra 地址 − 0x10000`。把两者混用会让钩子落在函数中段，表现是必崩。

判断标准：候选地址能在运行期 dump 里对上字节。只靠反汇编猜地址是不够的，因为相机上的模块和固件包里的可能不是同一次构建。

例子：想确认「音频信号」根节点在哪，先按 `.dynsym` 找到包内符号，再按"相机侧 = 包内 − 0x20"的规律换算，最后在真机 dump 里读 `0x162D39F8` 的属性表，六条记录逐条对上，才算定案。

## 第四步：用特征码固化

地址一旦确认，立刻记**特征**而不是只记偏移。下次换固件，扫一遍就能重新定位。

```bash
python tools/sigscan.py make --file logs/watch/usr_lib_libObj.so --va 0xA31226 --len 16
python tools/sigscan.py scan --file <你的 libObj.so> --pattern "7c 69 23 78 ?? ??"
```

判断标准：特征在目标文件里唯一命中；命中多处就把 `--len` 加长。

细节见[特征码定位](特征码定位.md)。

## 第五步：落盘并冷启动验证

前四步都只证明"静态上对"。落盘之后才算把结论钉住。

```text
L2 落盘正确性   write → sync → fsync /dev/nflasha15 → sync → 拔电池 → 读回
L3 运行时正确性 内存计数器增量、钩子字节在内存里、行为变化
```

判断标准：拔电池后 `/proc/uptime` 归零，SHA 不变，行为不变。

## 分层验证

三种"正确"必须分开回答，混在一起就会得到不可解释的结果。

| 层级 | 问题 | 常用手段 |
|---|---|---|
| L1 静态正确性 | 反汇编对、仿真过、边界对 | capstone 反汇编自检、Unicorn 仿真、负向用例 |
| L2 落盘正确性 | 改动真的进存储了吗 | 拔电池后读回；`fsync` 到块设备 |
| L3 运行时正确性 | 代码或数据真的被系统读到了吗 | 内存计数器、钩子字节读回、行为变化 |

常见错误推理：

| 常见假设 | 实际情况 |
|---|---|
| 钩子写好了，所以生效了 | 块根本没落盘 |
| SHA 一致，所以补丁成功 | 读的是页缓存 |
| 载荷仿真过了，所以真机没问题 | Unicorn 不检查对齐，不模拟硬件异常 |
| 改完没反应，所以代码写错了 | 可能没走到执行路径 |

## 证据强度

不标强度的结论会误导后来者。本项目用四档：

| 标记 | 含义 | 例子 |
|---|---|---|
| `[实测]` | 真机跑通并观察到效果 | 连拍 N 声、音量变大、拔电池后仍生效 |
| `[静态]` | 从 dump 或固件逐字节确证，逻辑闭环但未逐项上机 | `CpMsg` 结构、菜单 `_settingProperty` 布局 |
| `[推断]` | 有多条间接证据，没有判决性实验 | `priority ≥ 6` 被"静音机制"拦掉 |
| `[未验证]` | 只是设计或离线仿真 | LD_PRELOAD 持久化通道、路线 G 菜单方案 |

把 `[推断]` 和 `[未验证]` 当成 `[实测]` 用，是这个项目大多数惨痛教训的来源。

## 一个完整案例：连拍逐帧触发点

这是最能说明流程的一次。

现象：单拍能响，连拍只响一声。

假设 A：钩错了地方。 当时钩的是 `InputService::createEvent`。读反汇编发现它处理的是输入事件，`r1` 是 eventId，`0x32` 是快门全按。连拍时快门只按下一次，所以这个钩子天生只能响一声。假设 A 排除。

假设 B：CP 每帧会给 AP 发消息。 要验证得先看消息本身。钩 `osal_rcv_msg_tmo` 出口，把消息头写进环形缓冲。

```bash
python tools/build_payload/build_msglog_payload.py
python tools/inject/inject_generic.py --so <产物> --hook-va <osal_rcv_msg_tmo 出口>
python tools/analysis/read_msglog.py            # 拉回并解析
```

415 条记录解析出来：

```text
单拍 1 张：nid 0x1000 ×1，0x1001 ×1，0x1002 ×1，0x1007 ×1
连拍 8 张：nid 0x1000 ×1，0x1001 ×8，0x1002 ×8
```

`0x1001` 每帧一次，假设 B 成立。

定钩点：找 `0x1001` 的分发位置。最终选在 CP 收包循环 `FUN_00A311E0` 内、类型分发之前的那条指令，文件 VA `0xA31226`。选它的理由：完整指令边界、4 字节可重放、运行期确实执行、能拿到 `CpMsg` 指针。

写载荷：判据 `msg->type == 4 && msg->nid == 0x1001`，命中就组 `ObjMsg(0x3410, 0x1120)` 异步投递。约束是零 store、不阻塞、callee-saved 全保存。

验证：内存注入后拍一张响一声；连拍 5 张响 5 声；拔电池后仍然如此（落盘版）。

整个过程里每一步都有可观测证据。没有一步是"看起来应该对"。

## 探针设计规则

| 规则 | 原因 |
|---|---|
| 用内存计数器，不写文件 | 写文件会因 `open` 失败或会话降级丢证据 |
| 结构大小未确证时最多读 16 字节 | 读到未映射页直接崩 |
| 先写证据、再解引用 | 崩了也知道拿到的是什么 |
| 一次只加一个观测点 | 一次改三处，失败了不知道哪处错 |
| 观察类需求优先用用户可观察的行为 | 改设置听声音变化，比往数据库层插钩子可靠 |

### 通道本身的坑

探针不可靠时，数据比没有更糟。三种常见故障：

- **shell 回显污染解析**。`echo RC=$?` 的回显里含 `RC=`，读取器一看到就返回，拿到的是命令文本而不是结果。解决办法是用唯一标记（当时用 `Z9X`），或者只接受"整行都是纯十六进制"的行。
- **会话降级**。服务模式会话会插字、`xxd` 读回空、`readFile` 报 130。读失败要换通道（PMCA `readFile`、shell `xxd`、直接读 `/proc`）再判断。
- **重启脚本没有真的重启**。有时脚本只是结束了服务会话，相机并没有真的重启。判断依据是 `/proc/uptime` 归零，
不是命令返回成功。`tools/camera_scripts/cam_reboot_diag.sh` 会顺带核对 uptime。判据永远是 `/proc/uptime` 归零。

## 失败时先查什么

按顺序查，不要跳：

```text
1. 钩子字节在内存里吗？      busybox dd if=/proc/155/mem ... | busybox xxd -p
2. 落盘了吗？                拔电池后读回 SHA
3. 真的重启了吗？            /proc/uptime 归零
4. 走到执行路径了吗？        探针计数器
5. 最后才怀疑代码写错
```

## 崩溃与恢复

会遇到的形态：黑屏、按键无响应、过一会儿自己恢复、设置回滚。设置回滚是"载荷崩过"最可靠的指纹。

恢复顺序：

```text
1. 拔电池（最可靠的恢复手段）
2. 用原厂文件整块还原，核对整文件 SHA
3. 从内存注入版本重新开始，不要在旧补丁上叠加
```

让相机进入未知状态之前，先想好怎么恢复。

## 元教训

三条比具体技术更值钱的：

1. **验证顺序不能反**：静态验证、落盘验证、运行时探针，最后才谈功能。
2. **一次只改一个变量**：一颗探针、一个字节、一个结论。
3. **失败立刻回滚**：每次实验前恢复原厂，实验后恢复原厂并验证 SHA。

还有一条："没反应"时先怀疑"改动有没有到"，再怀疑"代码写错没"。 这个顺序搞反过至少五次。
