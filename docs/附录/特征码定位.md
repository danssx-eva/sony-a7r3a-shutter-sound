# 特征码定位

地址会随固件和构建变化，字节模式不会。特征码定位就是用一段短字节序列（允许通配）在自己的固件里重新找到同一个函数，把新偏移算出来。

## 影响

仓库里每个地址都是"某一个模块、某一个固件版本、某一次构建"里的偏移。它只对本项目记录的设备有效。照抄地址的后果不是"可能不生效"，而是"钩子落在别的函数中间，每次操作都崩"。

特征码是唯一能让这套东西跨版本、跨设备复用的办法。它和 Magic Lantern 的 `constable` 是同一个思路：工具不硬编码地址，而是先在用户的固件里定位函数。

## 地址不能照搬的证据

三条，都是实测：

```text
1. 相机上的 viewUnified2.so 是 10,752,440 字节，固件包里的同名文件是 10,752,148 字节
   两者的 setValueToModel 差了 0x120（包内 0x38BEE4，相机 0x38C004）

2. ILCE-7RM3 3.10 与 ILCE-7RM3A 1.00 的 libObj.so，
   同偏移处字节相同率只有 8.08%

3. 社区记录里 bootin.elf 是 13,116 字节，本机实测 13,068 字节，差 48 字节
```

第 3 条最容易被忽略：如果某个字符串的偏移恰好相同，容易误以为两份文件一样，实际上整份文件不同。相信别人文档里的偏移，就是这么踩进去的。

## 特征码是什么

一段 12 到 16 字节的十六进制字节序列，空格分隔，`??` 表示通配。

```text
7c 69 23 78 ?? ??      连拍钩点前后的一段
f8 b5 10 20 ?? af      单拍钩点附近
```

它有两个性质：

- 是**定位用的指纹**，不是可运行的代码，也不包含函数体
- 允许通配，因为函数内的绝对地址、寄存器分配在不同构建里会变

工具是 `tools/sigscan.py`。

## 工具用法

| 命令 | 作用 |
|---|---|
| `sigscan list` | 列出内置示例特征 |
| `sigscan locate --file <so> [--base <addr>]` | 逐个检查内置特征 |
| `sigscan scan --file <so> --name <sig>` | 定位单个内置特征 |
| `sigscan scan --file <so> --pattern "f8 b5 ?? 20"` | 定位自定义特征 |
| `sigscan make --file <so> --va 0x3C039E --len 16` | 从指定地址生成特征 |

输出的地址都是文件内偏移（fileVA）。给了 `--base` 会同时打印运行期地址。

```bash
python tools/sigscan.py list

python tools/sigscan.py locate --file my_libObj.so --base 0x05DCA000

python tools/sigscan.py make --file my_libObj.so --va 0x3C039E --len 16

python tools/sigscan.py scan --file my_libObj.so --pattern "f8 b5 10 20 ?? af"
```

## 换一台机器的流程

```text
1. 从相机上导出模块，例如 /usr/lib/libObj.so，并保留原厂文件
   用 tools/camera/a7r3a_watch_pull.py 或 cam_memdump_file.py

2. 跑 sigscan locate，看内置示例特征里哪些能匹配
   换固件版本后有特征不匹配是正常的

3. 对不匹配的特征，先手工定位一次那个函数，再在该偏移上跑 sigscan make 生成自己的特征
   手工定位可以用 who_calls.py、plt_map.py、xref_address.py 这些工具，也可以直接在 Ghidra 里找

4. 把新偏移用到原来用旧地址的所有地方
   笔记里记特征，不要只记偏移
```

判断标准：

- `make` 之后先 `scan` 一遍，确认唯一命中
- 命中多处就把 `--len` 加长，再做一次
- 特征落在函数入口的序言上更稳，落在中段遇到构建改动容易失效

## 内置特征

下面是本项目设备上的示例。它们的用处有两个：判断一份 dump 是不是同一构建，以及当写自己特征的模板。

| 模块 | 名称 | 文件偏移 | 用途 |
|---|---|---|---|
| libObj | `createEvent_hook` | `0x3C039E` | 单拍钩点 |
| libObj | `cp_recv_loop_hook` | `0xA31226` | 连拍钩点 |
| libObj | `plt_ObjMsg_ctor` | `0x0FF7B8` | PLT 桩 |
| libObj | `plt_ParamStd_ctor` | `0x102B34` | PLT 桩 |
| libObj | `plt_AddParam` | `0x1027E4` | PLT 桩 |
| libObj | `plt_IssueCommandAsync` | `0x0FD2A0` | PLT 桩 |
| libObj | `Get_id` | `0x34D840` | 组件查找 |
| viewUnified2 | `setValueToModel_cam` | `0x38C004` | 相机构建的入口点 |
| viewUnified2 | `setCursorOnItemChange` | `0x38BEB0` | 相邻函数，用来区分构建 |

每个特征 12 到 16 字节。如果匹配出多于一处，用更大的 `--len` 重跑 `make` 把特征加长。

## 和 verify_environment 的关系

`tools/verify_environment.py` 用的是固定偏移，因为它的目的就是回答"设备与记录的是否一致"。所以顺序是：

```text
1. 先跑 verify_environment.py --check-all
2. 报不匹配时，再用 sigscan 在构建上找真实偏移
```

先定位再检查会浪费一轮；先检查再定位能立刻知道自己是"同一构建"还是"需要重新找"。

## 局限

- 周围代码一变，特征就失效，尤其是入口函数序言被改动的构建。
- 通配符会降低唯一性。`sigscan` 会报告匹配数量，自己判断。
- 内置示例特征是从本项目设备 dump 里提取的短模式，不是代码副本。
- 特征码只能定位"函数在哪"，不能告诉你"这个函数在本地构建里语义是否一样"。语义要用运行期探针确认。

## 写法约定

在文档和笔记里记录一个地址时，写三样东西：

```text
名字       CP 收包循环钩点
特征       7c 69 23 78 ?? ??（sigscan 名称 cp_recv_loop_hook）
偏移       fileVA 0xA31226（仅本机 fw 1.00 有效）
证据       运行期读回一致；连拍 N 张响 N 声
```

只写偏移的笔记，换一台机器就是废纸。只写特征不写证据，下一个人的第一反应会是"这凭什么"。

## 什么时候该重新定位

| 情况 | 是否要重新定位 |
|---|---|
| 换了一台同型号同固件的相机 | 要。区域版本和硬件批次都可能不同 |
| 同一台相机重新 dump | 不必，但要核对 SHA |
| 换了固件版本 | 要。所有模块都可能变 |
| 相机上的模块与固件包里的同名模块 | 要。这两者本来就不是同一次构建 |
