# 死路清单

这是本仓库最值钱的一篇。它不写成功学，只写试过并且确认走不通的路，以及确认做不成的事。

每条的结构固定：**假设是什么、真相是什么、代价多少、正确做法是什么**。看完这一篇，至少能少花三天。

## 怎么读

证据强度有四种标记：

| 标记 | 含义 |
|---|---|
| `[实测崩溃]` | 真机上崩过或卡死过，有恢复记录 |
| `[实测无效]` | 真机上跑过，没有效果（不是崩，是没用） |
| `[静态判定]` | 从固件或内存数据分析得出，未上机验证 |
| `[设计否决]` | 按设计约束主动放弃（实时性、安全性、风险），不是试了失败 |

证据档位与[逆向方法](逆向方法.md)的对应关系：`[实测崩溃]`/`[实测无效]` → `[实测]`，
`[静态判定]` → `[静态]`；`[设计否决]` 是主动放弃，不属于证据档位。

所有地址只对 ILCE-7RM3A / 固件 1.00 / 本机这次 dump 有效。

条目编号按主题分组：A 存储与持久化、B 注入通道、C ARM/Thumb 汇编、D 声音链路、E 菜单系统、F 方法论、G 新增音效、U 未完成项。

这些路一共花掉：崩过 10 多次应用（黑屏、按键无响应、自己恢复、设置回滚）、死锁 2 次（只能拔电池）、白干 3 个半天（落盘假阴性、格式没破解、地址差 0x120）、推翻 3 个已经写进文档的错误结论。

## A 组：存储与持久化

这一组踩得最惨。大部分"钩子无效"不是代码错，而是改动根本没到闪存。

### A-01 用 `busybox dd` 原地写闪存文件，文件被截断 [实测崩溃]

- 假设：`busybox dd if=patch.bin of=/usr/lib/libObj.so bs=1 seek=1654784 count=2` 只改偏移 1654784 的 2 个字节。
- 真相：busybox 的 `dd` 以 `O_TRUNC|O_CREAT` 打开输出文件，精简版没有 `conv=notrunc`。写到哪里就在哪里截断。100 字节的文件 `seek=50 count=2` 之后变成 52 字节。
- 代价：第一次尝试持久化就把 `/usr/lib/libObj.so` 写成 100 字节以下，靠备份恢复。
- 正确做法：自己写一个不带 `O_TRUNC` 的写工具：`open(path, O_WRONLY)`、`lseek`、`write`、`fsync`。本项目产出了 `tools/inject/pw_nolibc.c` 加 `pw_start.S`（无 libc、纯 syscall、228 字节）。

### A-02 把"会话内 SHA 一致"当成"已经落盘" [实测无效]

- 假设：写完立刻 `sha256sum`，一致就是成功。
- 真相：读的是 page cache。eMMC 的写回缓存没刷，断电或重启全部回滚。
- 代价：一整晚的工作。第二天重启发现回到原厂。
- 正确做法：判据只有一条，**真冷启动后再读一次**。

### A-03 以为 `sync()` 会把写回缓存刷进闪存 [实测无效]

- 假设：`busybox sync` 之后写入就安全了。
- 真相：`sync()` 只把内核脏页交给块层。eMMC 自己的写缓存要 `fsync` 到块设备才会被要求落盘。
- 代价：早期所有"补丁无效"结论的根源，其中至少两轮"换钩点"排查完全是空的。
- 正确做法：

  ```sh
  mount -o remount,rw /usr
  # 写
  busybox sync
  busybox fsync /dev/nflasha15
  busybox sync
  mount -o remount,ro /usr
  ```

### A-04 以为"全套仪式都做了就一定落盘" [实测无效]

- 假设：`sync` 加 `fsync` 加 `drop_caches`，都做了就该落盘。
- 真相：有反例。块 `0x295000` 写入成功、立即回读一致、`drop_caches` 后仍一致，**重启必回滚**。ext2 的元数据、坏块、写回策略都可能导致某些块系统性不落盘。
- 代价：把"仪式"当成了保证，而不是提高了概率。
- 正确做法：逐块写、逐块重启后验证。这是最终只改 2 个块、并且这两个块单独验证过的原因。

### A-05 在 ext2 上原地改几个字节，不持久 [实测无效]

- 假设：文件系统会只改那几字节。
- 真相：ext2 的间接块和元数据可能把整块重写回旧版本，文件系统缓存也会吞掉改动。
- 代价：多轮"改了没反应"。
- 正确做法：要么按 1 KB 块整块覆盖写，要么用自制写工具加 A-03 的仪式，再加冷启动验证。最终方案是整块覆盖加逐块验证加整体 SHA 交叉确认。

### A-06 以为直接写块设备更可靠 [实测无效]

- 假设：绕过文件系统直接写 `/dev/nflasha15` 更直接。
- 真相：同样不持久，而且更危险。绕过文件系统之后，ext2 元数据与实际数据不一致。
- 代价：一次可能导致文件系统损坏的实验。
- 正确做法：走文件系统层加正确的刷盘仪式。块设备只在明确知道自己在干什么时才碰。

### A-07 用普通重启当冷启动 [实测无效]

- 假设：`busybox reboot` 之后就是一次新的运行。
- 真相：`nflasha5` 是 WBI 热启动快照（643 个 LZ77 段），普通重启会把 RAM 内容跨重启复用，`boot_id` 甚至可能不变。
- 代价：多次"改了没生效"其实是旧状态残留。
- 正确做法：拔电池等十几秒才是真冷启动。判断有没有真的重启，看 `/proc/uptime` 是否归零。

### A-08 回滚清单漏登记钩点所在的块 [实测无效]

- 假设：还原脚本只要写回"载荷块"就够了。
- 真相：旧版清单里没有钩子块 `0xC19800` 和处理函数块 `0x293800`，还原完整文件 SHA 回不到原厂的 `f1351204…`，留下悬空跳转。
- 代价：一次错误的"已还原"判断。
- 正确做法：每新增一个钩点，必须同时把它的块加进还原清单。还原后核对整文件 SHA256 与出厂值完全一致。

### A-09 把服务模式会话里读到的内容当成闪存内容 [实测无效]

- 假设：读失败就是文件没有那段数据。
- 真相：服务模式会话会降级，PMCA 报 `Senser file control error 130`、shell 输出插字、`xxd` 读回空。
- 代价：一轮"换钩点"排查完全是空的。
- 正确做法：读失败要换通道重试（PMCA `readFile`、shell `xxd`、直接读 `/proc`），再下结论。

## B 组：注入通道与执行环境

### B-01 看到 `LD_PRELOAD` 机制存在，就以为能用 [实测无效]

- 假设：相机自带一条注入链，逐字节核实过就说明可用。

  ```text
  /usr/bin/bootin.elf 读 /setting/mode/dmode
  含 'p' 就读 /setting/mode/preload
  拼成 LD_PRELOAD="…" im.elf
  /usr/bin/change_mode.sh 官方脚本里就有 p 选项
  ```

- 真相：**bootin 运行时 `/setting` 还没挂载**，`open()` 失败，flags 读成 0，不加载。同一时刻 `/setting/env.txt` 也不可读。
- 代价：一整轮的 `.so` 开发和部署脚本。
- 正确做法：在挂载之后的时机注入；或者直接用 `/proc/<pid>/mem`（本项目所有成功证据都来自它）；磁盘补丁是另一条路（能持久但写入不可靠）。

### B-02 用 `/etc/ld.so.preload` 做持久化 [设计否决]

- 假设：用系统级 preload 文件可以在启动时加载自己的 `.so`。
- 真相：社区记录（A7 系列改机）里，这是当年变砖的元凶。glibc 2.11 下 preload 解析失败会直接起不来。
- 代价：无，本项目从未尝试。
- 正确做法：想都别想。

### B-03 假设"固件包里的地址等于相机运行期地址" [实测崩溃]

- 假设：从官网 `Update_ILCE7RM3V310.exe` 解包拿到 `viewUnified2.so`，Ghidra 里找到 `setValueToModel` 在 `0x38BEE4`，换算运行期 `0x15393EE4`，在那里打 4 字节钩。
- 真相：相机上的模块与固件包里的不是同一个构建。

  ```text
  固件包副本 10,752,148 B   setValueToModel @ 0x38BEE4
  相机副本   10,752,440 B   setValueToModel @ 0x38C004    差 +0x120
  ```

  `0x15393EE4` 落在 `setCursorOnItemChange` 中段，钩子横跨一条 4 字节 Thumb 指令的中间，返回地址非法。
- 代价：每次光标移动都崩，反复多轮，得出过"注入代码必崩"的错误结论。
- 正确做法：先把相机上的模块 dump 下来，用相机副本算地址；钩点前必须确认覆盖的 4 字节是完整指令边界。

### B-04 拿 A7R3（7RM3 3.10）的偏移去对 A7R3A（1.00） [静态判定]

- 假设：同属 CXD90045，结构相近，偏移可以直接借用。
- 真相：两版 `libObj.so` 同偏移相同字节只有 8.08%。7RM3A 没有官方固件包（已核实官方下载页无固件条目），只能用自己的机器 dump。
- 代价：早期很多"地址找不到"的困惑。
- 正确做法：3.10 只当结构参考。一切最终偏移以本机 dump（本机 dump 的 `libObj.so`，SHA `f1351204…`）为准，上机前用内存读交叉验证。

### B-05 相信别人文档里的偏移 [实测无效]

- 假设：社区记录说"本机与 A7R3 的记录完全相同"，那就相同。
- 真相：`bootin.elf` 本机 13,068 字节，A7R3 记录 13,116 字节。某个字符串偏移恰好相同纯属运气。
- 代价：按错误的偏移做了一轮分析。
- 正确做法：任何外部地址，必须在自己固件上逐字节验证后才能用。

### B-06 把"ELF 文件里的零区"当成"运行时空闲区" [实测崩溃]

- 假设：`libObj.so` 里 `0xFF3E90` 起有 20,974 字节全零，可以随便放载荷。
- 真相：那是 `.bss` 的影子区域，运行期被真实数据填满。
- 代价：多次崩溃。
- 正确做法：先 dump 运行时内存，确认那块地址在运行期也全是零、且不在任何已分配对象里，再放东西。

### B-07 假设 `rw-` 段可以执行 [静态判定]

- 假设：可写段里放代码，跳过去就能跑。
- 真相：`/proc/<pid>/maps` 里 `rw-p` 的段是 NX，跳进去立刻取指异常。决定权限的是 ELF 的 `PT_LOAD` 标志，不是 section 的 `SHF_EXECINSTR`。看 section flags 会得出错误结论。
- 代价：一次崩机。
- 正确做法：代码只放在 `r-x` 段的尾部空白。要放数据就找已验证可写且无人用的字节区，本机唯一验证通过的是 `libosal_uipc.so` 的 `.bss` 尾部 `0x0405EFE0..0x0405F000`，32 字节。

### B-08 在 CP 收包线程里读 Backup 或读文件 [实测崩溃]

- 假设：钩子里顺手读一个设置值，问题不大。
- 真相：`Bkup_Read` 是同步 IPC。CP 收包线程一阻塞，整条消息流水线停住。读文件同理，会走存储栈。
- 代价：整机卡死，拔电池。
- 正确做法：CP 线程里只做内存判断和异步投递。需要在启动期读一次的设置，放到启动时的一次性初始化里读。

### B-09 在 CP 收包线程里 `mmap` 分配 [实测崩溃]

- 假设：载荷需要一个缓冲区，临时申请一块内存。
- 真相：这是"在错误的地方做重活"，与 B-08 同类。
- 代价：崩机；改成零分配之后一次就过。
- 正确做法：载荷内不做任何分配。需要缓冲就用已验证可写的固定小区域（如 B-07 的 32 字节）。

### B-10 暴力扫 `/dev/mem` 找东西 [设计否决]

- 假设：反正能读 `/dev/mem`，全扫一遍总能找到。
- 真相：会踩到设备寄存器和未映射页，轻则崩进程，重则整机死。
- 代价：无，主动放弃。
- 正确做法：只做已知 ELF 段的 `mmap` 加受保护的访问。

## C 组：ARM 与 Thumb 汇编

这一组几乎每条都花掉半天。Unicorn 仿真能抓住一半，另一半只能靠上机。

### C-01 载荷布局写成"代码、数据" [实测崩溃]

- 假设：把路径字符串紧跟在代码后面最省空间。
- 真相：代码结尾是 `pop`，执行完顺序执行进了字符串字节，当指令执行。
- 代价：一天崩 4 次。表现是黑屏、Fn 键无响应、过一会儿自己恢复、**相机设置回滚**。
- 正确做法：布局固定为 `代码 → 重放被覆盖的原 4 字节 → b.w 跳回 → 对齐填充 → 数据`。

### C-02 字访问不保证 4 字节对齐 [实测崩溃]

- 假设：`str.w r6, [sp, #1]` 只是慢一点。
- 真相：ARMv7 对非对齐字访问抛异常。而 **Unicorn 不检查对齐**，仿真完全没报错。
- 代价：仿真通过、真机必崩。
- 正确做法：所有 `ldr`/`str` 的字访问地址 4 字节对齐；栈偏移自己数清楚。

### C-03 跨段 `bl` 调用，LR 被覆盖 [实测崩溃]

- 假设：双钩方案里 A 段（30 字节）`bl` 到 B 段（182 字节）再返回。
- 真相：B 段 `bx lr` 跳到了错误地址。
- 代价：拍一张就重启。
- 正确做法：载荷必须是单块连续函数，结尾用 `pop.w {…, lr}` 从栈恢复返回地址，不要用 `bx lr` 手工返回。

### C-04 改了 callee-saved 寄存器但没保存 [实测崩溃]

- 假设：用 `sb`（r9）存 soundId，push 列表里没有它也没关系。
- 真相：目标函数的原序言还没执行，你的调用污染了调用者状态。
- 代价：按一下键就重启。
- 正确做法：push/pop 覆盖所有动过的 callee-saved，即 r4–r11（含 sb/sl/fp）。连拍载荷的写法是 `push.w {r0-r3, r4-r8, r12, lr}`，仿真里逐项核对 9 个寄存器恢复原值。

### C-05 用 `adr r12, #0` 算模块基址 [实测崩溃]

- 假设：`adr` 加低 12 位就是一条普通指令。
- 真相：keystone 把 `adr r12, #0` 汇编成 `subw ip, pc, …`（高寄存器形式），capstone 认不出这是 `adr`，基址计算代码找不到它，基址是垃圾。
- 代价：崩机，且反汇编看起来"没问题"。
- 正确做法：用低寄存器（`adr r0` / `adr r4`），再 `movw`/`movt` 加 `sub` 得到基址；构建器用 capstone 反汇编回读 `adr` 的地址来算偏置。

### C-06 `ldrh r6, [r8, #2]` 汇编直接失败 [静态判定]

- 假设：高寄存器做基址的 load 指令应该能编。
- 真相：Thumb 编码不允许，keystone 报错。
- 代价：构建失败。
- 正确做法：先 `mov` 到低寄存器再 `ldrh`。

### C-07 用 keystone 的 `.inst.w` 重放原始字节 [静态判定]

- 假设：把那 4 字节写成 `.inst.w` 就能原样重放。
- 真相：keystone **静默丢弃** `.inst.w`，重放出来的字节可能不是原来的。
- 代价：钩点回跳后行为错乱。
- 正确做法：重放原 4 字节一律用二进制拼接（`payload = code + orig[hook:hook+4] + …`），不要交给汇编器。

### C-08 从 Thumb 符号地址（奇数）直接反汇编 [静态判定]

- 假设：`.dynsym` 里的地址就是函数入口。
- 真相：Thumb 函数地址是奇数（如 `0x6B7D01`），bit0 表示 Thumb 状态。从奇数地址开始反汇编全是垃圾。
- 代价：一轮"这里怎么不是这个函数"的困惑。
- 正确做法：用偶数基址（`0x6B7D00`）反汇编；地址只在与 `bx`/`blx` 配合时才 `|1`。

### C-09 用 `bx` 跳到偶数地址 [实测崩溃]

- 假设：跳转目标就是函数地址，不用管奇偶。
- 真相：偶数会切到 ARM 模式，后续指令按 ARM 解码。
- 代价：崩机。
- 正确做法：跳转目标 `|1` 保持 Thumb。

### C-10 跳板只保存 `{r0-r3, r12, lr}` [实测崩溃]

- 假设：r4–r11 是别人要用的，跟我无关。
- 真相：目标函数的原序言（如 `push {r4-r8, sb, sl, fp, lr}`）还没执行，插入的调用不守 AAPCS 就会污染 r4–r11。
- 代价：随机崩机。
- 正确做法：`push {r0-r3, r4-r11, r12, lr}`，并注意 8 字节栈对齐。这个组合是 60 字节，对齐 OK；`{r0-r3, r4-r8, r12, lr}` 是 44 字节，必须补 4 或 12 字节。

### C-11 拿到指针就解引用 [实测崩溃]

- 假设：读 `[this+0x220]` 得到的值就是堆指针。
- 真相：那个值可能是 rodata 或 vtable 地址，解引用读到未映射区。
- 代价：崩机，而且不知道崩在哪。
- 正确做法：解引用前 `cbz` 加范围校验，并且"先写证据、后解引用"，先把拿到的东西记到安全区再用。

### C-12 探针一次读太多字节 [实测崩溃]

- 假设：记录消息头，从 16 字节加到 64 字节更能看清结构。
- 真相：结构没那么大，读到未映射页。
- 代价：崩机。
- 正确做法：结构大小未确证前最多读 16 字节，并且分块读。

### C-13 在写卡路径上做文件 I/O [实测崩溃]

- 假设：`0xa3628c` 每张照片约调用 10 次，很适合当触发点。
- 真相：在那里 `open`/`write`/`close` 会导致存卡失败、拍照卡顿。还原后立刻正常。
- 代价：一次差点以为相机坏了。
- 正确做法：快门和存储路径上禁止任何额外 I/O 与耗时调用。这是硬约束。

### C-14 在拍照临界区里同步调用会取锁的接口 [实测崩溃]

- 假设：在 `0xc19b38`（持锁中）直接调 `beepPlay(3)`。
- 真相：beep 播放受 `SysConstraintBeepPlay` 资源约束保护，与拍照路径互锁。整机卡死，电源开关都关不掉，只能拔电池。
- 代价：死锁两次。
- 正确做法：临界区里只能异步投递或置标志。

### C-15 把 Ghidra 地址当成 fileVA [实测无效]

- 假设：反汇编器里看到的地址就是文件偏移。
- 真相：Ghidra 默认 imageBase 是 `0x10000`，`fileVA = Ghidra 地址 − 0x10000`。
- 代价：`ReadSoundFile` 写成 `0x1953bc`（正确 `0x2953bc`）、`mp_lEvtSndCmd` 写成 `0x0128cf50`（正确 `0x0129cf50`），一度钩错地方。
- 正确做法：每个地址都标注它是 fileVA 还是 Ghidra 地址，上机前用内存读交叉验证。

### C-16 载荷里 store 到未证实的内存 [实测崩溃]

- 假设：找一块"看起来没人用"的内存写进去就行。
- 真相：踩过的地址有 `0x070A6000`（覆盖程序活动数据）、`0x0405EFE8 + 32`（越界到未映射页），`mmap` 动态分配也崩过。
- 代价：多次崩机。
- 正确做法：零 store。最终成功的连拍载荷一条 store 都没有，仿真时用 `UC_HOOK_MEM_WRITE` 全程监控确认。

### C-17 载荷里 `sub sp` 之后又 `push`，栈对齐变了 [实测崩溃]

- 假设：栈帧自己算一次就行。
- 真相：中途再 push 会改变对齐，后面的字访问就踩到非对齐异常。
- 代价：崩机，且现象与 C-02 混在一起难以区分。
- 正确做法：载荷内固定一个栈框架，所有偏移一次算清，中途不再动 sp。

## D 组：声音链路

### D-01 以为音效文件是裸 PCM [静态判定 + 实测]

- 假设：把 WAV 当 8 位有符号 PCM 直接塞进去。
- 真相：每 32 字节一块，1 个控制字节加 31 个 int8 残差，一阶预测器系数 60/64，24 kHz 单声道。
- 代价：声音没变或者变成噪音。
- 正确做法：用同一套编解码器，并做回环验证：解原厂文件、重编码、误差接近 0（实测 1/20401）。

### D-02 得出"替换音效文件毫无效果"的结论 [实测无效，已推翻]

- 假设：三次替换（含替换成纯静音）加冷启动，声音完全不变，所以替换无效。
- 真相：替换是有效的。当时文件格式没搞对（不是裸 PCM），测法也有问题（只比了前 32 字节）。
- 代价：约一天，而且这个错误结论一度被写进交接文档。
- 正确做法："改了没效果"时先怀疑"我改的东西真的是它读的东西吗"。这类结论要标证据强度和验证层级。

### D-03 想用 `priority 6` 的真快门声音效 [实测无效]

- 假设：直接把真正的机械快门声放进本项目的槽位，音色最像。
- 真相：`0x01` KA、`0x02` SHA、`0x03` KASHA、`0x05`、`0x06`、`0x37` 播不出来，被静音或优先级机制拦掉。
- 代价：多轮实验。
- 正确做法：用 priority ≤ 5 的槽位承载，音色由替换进去的音频决定。本项目用 `0x07` CAUTION。

### D-04 把 `Param 0x1001` 设成 255 [实测无效]

- 假设：255 表示"一直播"，正好适合连拍。
- 真相：255 是无限循环，只有新的焦点事件能打断。
- 代价：相机一直在响。
- 正确做法：`0x1001 = 1`（单次）。

### D-05 同步调用播放接口 [实测崩溃]

- 假设：直接调播放函数比组消息简单。
- 真相：与 C-14 同一个死锁，拍照临界区里同步调用取锁的接口会卡死整机。
- 代价：拔电池两次。
- 正确做法：`ObjMsg` 组包加 `IssueCommandAsync` 异步投递。

### D-06 把"投递返回 0"当成"播放成功" [实测无效]

- 假设：`IssueCommandAsync` 返回 0，说明消息送达并播放了。
- 真相：0 只是 EventSender 的返回值。
- 代价：一轮"已经响了却以为没响"的排查。
- 正确做法：成功判据必须是听到声音，或下游处理函数（`vt[9]`）命中计数增加。

### D-07 从"Linux 侧没有音频设备"推出"声音做不出来" [静态判定，已推翻]

- 假设：`/dev` 77 个节点里没有 `snd/dsp/adf/pcm/codec`，没有 `/proc/asound`，`/proc/devices` 也没有音频类，所以声音不可能。
- 真相：Linux 确实不能直接发声，但可以用异步 IPC 请 RTOS 播。"没有输出设备"和"不能请求别人播"是两件事。
- 代价：这条结论写进了交接文档，差点终止项目。这是本项目最大的一次误判。
- 正确做法：否定性结论要写成"在 X 前提下做不到"，不要写成"做不到"。另外还有一条"`avsystemsound/*.bin` 从不被播放"，同样在后来被推翻（D-02）。

### D-08 钩 AP 侧 `M_BEEP::Execute` 想让电子快门发声 [实测无效]

- 假设：这是 AP 侧播放全部提示音的入口，钩上去应该就能响。
- 真相：电子或静音快门下这个函数根本不被调用，发声决策完全在 CP 内部。
- 代价：一轮实验。
- 正确做法：不要在 AP 侧找播放入口，去 CP 侧找触发点。

### D-09 钩 `InputService::createEvent` 想实现连拍逐帧 [实测无效]

- 假设：每次快门都经过这个函数。
- 真相：这是按键输入事件。连拍时快门只按下一次。
- 代价：单拍正常，连拍只响第一声。
- 正确做法：钩 CP 收包循环，过滤逐帧消息 `nid == 0x1001`。

### D-10 钩 `MprIf::SetRemainCaptureCount` 想每帧触发 [实测无效]

- 假设：剩余张数每帧都变，这个函数应该每帧都调。
- 真相：`libmpr.so` 导出符号，入口干净可钩（`0x884A7C`），载荷也确实跑起来了，但只在换卡或改画质时调用。
- 代价：一轮实验。
- 正确做法：要逐帧就认逐帧消息，不要从"名字看起来相关"的函数推。

### D-11 找"看起来像写文件"的函数当快门信号源 [静态判定]

- 假设：引用 `"WriteFileData"` 的 `FUN_00ca05ec`、引用 `"writeImageToFile"` 的 `FUN_00d01550` 是写文件路径的一部分。
- 真相：Ghidra 反汇编显示它们都只是日志消息构造函数（`add rX, pc` 拼日志字符串）。
- 代价：一轮分析。
- 正确做法：函数的真实语义看调用点和参数，不看它引用哪个字符串。

### D-12 只比前 32 字节来验证音效替换 [实测无效]

- 假设：文件头一样就说明替换成功。
- 真相：会漏掉"前面是静音、后面才是声音"的情况，得出"没变"的错觉。
- 代价：一次误判。
- 正确做法：比整个文件的 MD5。

### D-13 一次 `writeFile` 传大文件 [实测无效]

- 假设：一次传完 8640 字节没问题。
- 真相：`camera.writeFile` 超过约 28 KB 会失败。
- 代价：上传中断，文件不完整。
- 正确做法：每段不超过 4096 字节，分段上传后在相机上 `busybox cat` 拼接。

### D-14 把三套"音量"混为一谈 [实测无效]

- 假设：调大"音量"就是调大声音。

  | 位置 | 范围 | 说明 |
  |---|---|---|
  | Backup 音量字节 | 0..7 | 本项目改的就是这个（`0x002B0020` 等） |
  | `ObjSpeaker::ExecCmdSetVol` 的 param `0x1002` | 1..16 | 另一套，未验证 |
  | 菜单「音量设置」16 档 | 0..15，显示与内部反序 | 「Zero」存 `0xF` |

- 真相：三套各自独立，改错了不会有任何效果。
- 代价：一次"我明明调大了却没变响"。
- 正确做法：认准 Backup 字节，写完重启。

## E 组：菜单系统

这一组的共同点：看起来能改，改完不生效，而且不报错。

### E-01 以为菜单可以随便加一项 [静态判定，实测印证]

- 假设：往菜单节点树里插一个节点就行。
- 真相：`CautionConfig.so` 里的设置行是扁平列表，不是树，456 个槽位全部占满，count 变量在另一个独立位置（`0x1646D00C`）。
- 代价：多套方案失败。
- 正确做法：加一项要同时动属性表（rodata）、节点对象（BSS）、`tbb` 跳转表、父节点 `subNodes` 数组、全局 count。先确认这些地方都有空间，再谈方案。

### E-02 只改 `subNodes` 指针或 `count` 想让新行显示 [实测无效]

- 假设：节点自己的子节点数组和计数决定显示什么。
- 真相：显示路径走的是扁平行列表加 `getCountSelectable()`，改节点自己的 `subNodes`/`count` 对这一层没有影响。
- 代价：两轮无效实验。
- 正确做法：不要在节点对象上使劲，去看渲染层的行列表。

### E-03 往「音频信号」这个值选择器里加叶子节点 [实测无效]

- 假设：在「音频信号」的选项列表里加一个第 3 项「开/关」，就能当开关用。
- 真相（已定位到指令）：

  ```text
  菜单确认
    → CmnSettingNodeUtil::setValueToModel()（相机 0x38C004）
        procId 取自【行节点】的 prop 0x0E，叶子只提供值 prop 0x0F/0x10
        → comp->vtbl[0x44](comp, procId, value)    CmnViewProcessDataMgr::setValue → 0x2E5560
        → element->vtbl[0x58](element, value)      CmnViewProcessDataElementNormal::setValue(int) → 0x424614
        → 校验 0x4244F2（"允许值集合"成员判定）
        → 失败：静默 return 1，不写模型
        → UI 下一帧按模型旧值回显，用户看到"回退"
  ```

  值 6/7 被解释成 procId `0xA8` 的第 6/7 项，而合法集合里没有它，在模型元素层就被丢弃。
- 代价：多轮"为什么选中没反应"的排查，换过 4 套方案。
- 正确做法：不要在值选择器里加叶子。要开关就用原生二值开关行，或者借用原生设置行（见 E-06 末尾与路线 G）。

### E-04 以为那 5 个「音频信号」节点对象反映当前设置 [静态判定 + 实测]

- 假设：读节点状态就知道当前是开还是关。
- 真相：`On / Shutter / OnlyShutter / Off / OffShutter` 是 BSS 里的静态模板。设置从开改成关之后，状态字完全不变（`On=2, Shutter=0, OnlyShutter=0, Off=1, OffShutter=0`）。
- 代价：一轮无效的读取方案设计。
- 正确做法：真正的值只能从 Backup `0x01070026` 读；而 `Bkup_Read` 在 CP 线程里是死锁源（B-08）。

### E-05 钩 `setValueToModel` 观察菜单提交，反复崩溃 [实测崩溃]

- 假设：在这个函数上钩一下就能看到所有菜单提交。
- 真相：直接原因是地址错 `0x120`（见 B-03），钩在了 `setCursorOnItemChange` 中段。真入口是相机 `0x38C004`（运行期 `0x15394004`），前 4 字节是 `push {r4,r5,r7,lr}` 加 `sub sp,#8`，正好两条完整 2 字节指令，天然适合 4 字节钩子。
- 代价：反复崩溃多轮。
- 正确做法：改对地址可行，但要注意这个函数是所有设置行共用的普通成员函数，没有"只被本项目的菜单项调用"的单点（见 E-06）。

### E-06 想找一个"只被菜单确认操作使用"的函数或指针 [静态判定]

- 假设：只要有这样的单点，挂逻辑上去就成。
- 真相：不存在。路线 E 的前提也不成立：`0xFB7C` 只是 `.dynsym` 里 `_ZN18CmnSettingNodeUtil15setValueToModelEv` 的 `st_value` 字段，全镜像没有任何代码或数据引用它，写它零影响。粒度最细的单点是相机 GOT 槽 `0x158D4BBC`（只影响 `viewUnified2` 内那 1 个调用点），但目标函数必须是已存在的函数，没有哪个已有函数会记录本项目的开关。
- 代价：一轮方案设计后放弃。
- 正确做法：承认没有单点。要么走纯数据的路线 G，要么不做独立开关。

### E-07 钩 `Bkup_Write` 想观察或拦截菜单写入 [实测崩溃]

- 假设：钩住写入层就能看到相机有没有尝试写本项目的 BKID。
- 真相：钩子上机反复崩，地址和上下文都不对。
- 代价：多次崩机。
- 正确做法：观察类需求优先用用户可观察的行为（改设置、听声音变化），而不是往数据库层插钩子。

### E-08 改 `.uxc` 文本资源想"新增"菜单条目 [静态判定]

- 假设：菜单文字在 `.uxc` 里，加一条就行。
- 真相：`.uxc` 只能原地改已有字符串（等长替换），不能新增条目。条目数和资源 ID 在别处被索引。
- 代价：一轮分析。
- 正确做法：能做的是改文案，已有工具 `tools/analysis/uxc_strings.py`、`tools/camera/a7r3a_zh_label.py`。

### E-09 直接拿固件包里的属性表地址去补丁 [静态判定，实测校验]

- 假设：包内有符号，地址直接能用。
- 真相：相机侧 `CautionConfig` 的属性表地址等于包内同名符号地址减 `0x20`，对 dump 里 696/696 个带 procId 的设置行全局验证通过。用包内地址会读到隔壁表，表现为"写进去没反应"。
- 代价：一轮无效写入。
- 正确做法：按 `−0x20` 换算，并且用真机 dump 核对首条记录。

### E-10 以为 BSS 里还有空间放新对象 [静态判定 + 实测]

- 假设：dump 里看起来全零的地方就是空的。
- 真相：`CautionConfig.so` 的 BSS 被 52,614 个符号填满。看起来全零的"空闲区"（如 `0x1651F798` 起 2152 字节）在实验期内其实已经带注入痕迹。
- 代价：一次基于脏数据的方案评估。
- 正确做法：要放数据先重启相机清干净，再运行时读回确认全零，然后才用。

## F 组：方法论

这些"不是技术问题"的问题最贵。

### F-01 先怀疑代码，后怀疑环境 [设计否决]

- 假设：没反应就是代码写错了。
- 真相：三天里的真实循环是"写代码、上机、没反应、猜原因、再写"。复盘发现每次失败几乎都不是代码错，而是改动没有到达它该到的地方。

  | 以为 | 实际上 |
  |---|---|
  | 钩子写好了，应该生效了 | 磁盘块根本没落盘 |
  | SHA 一致，补丁成功 | SHA 读的是缓存 |
  | `LD_PRELOAD` 机制存在，能用 | `/setting` 那一刻还没挂载 |
  | 投递返回 0，消息送达 | 0 只是 EventSender 返回 |
  | 代码里有发声分支，会响 | 分支运行时可能没被走到 |

- 代价：三天里至少五次把顺序搞反。
- 正确做法：先查"改动有没有到"，再查"代码有没有错"。

### F-02 把三种"正确"混为一谈 [设计否决]

- 假设：验证就是验证。
- 真相：L1 静态正确、L2 落盘正确、L3 运行时正确是三件事，经常跳过 L2 和 L3。
- 代价：大量不可解释的实验结果。
- 正确做法：任何一次上机测试，先回答 L2 和 L3 各自的状态。

### F-03 一次改三个变量 [设计否决]

- 假设：一起改省时间。
- 真相：失败时无法定位。
- 代价：多个半天。
- 正确做法：一颗探针、一个字节、一个结论。

### F-04 在旧补丁上叠新补丁 [设计否决]

- 假设：上一层已经验证过，直接叠就行。
- 真相：出问题后无法判断是哪一层。
- 代价：浪费在归因上的时间。
- 正确做法：每次实验前恢复原厂，实验后恢复原厂，并验证 SHA。

### F-05 把"读不到"当成"没执行" [设计否决]

- 假设：读回来是空，说明没写进去或没执行。
- 真相：服务模式会话降级时读回为空，文件可能已经写成功了。
- 代价：浪费一整轮"换钩点"排查。
- 正确做法：换通道重试后再判断。

### F-06 过早下结论，并把它写进交接文档 [设计否决]

- 假设：当前证据足够下结论。
- 真相：三个典型错误结论后来全部被推翻："Linux 无音频设备所以声音做不出来"（D-07）、"替换音效文件无效"（D-02）、"注入代码必崩"（B-03，部分原因是地址错）。
- 代价：差点终止项目。
- 正确做法：否定结论必须带前提与验证层级，并标注证据强度。

### F-07 直接采信子代理或他人给的偏移 [设计否决]

- 假设：别人核对过的东西可以直接用。
- 真相：见 B-05，子代理说"本机与 A7R3 记录完全相同"，实测差 48 字节。
- 代价：一轮错误分析。
- 正确做法：自己逐字节核对。

## U 组：未完成项

目标是在菜单里加两项：「电子快门声 开/关」和「声音选择」。结果是子菜单里能显示（"开/关"两项），选中后会回退。这不是"没写对"，是结构上被挡住，原因见 E-03。

还缺什么：

1. 路线 G 的只读验证（已设计，未上机）：借一个原生二值开关行，把它的 props 表指针指向 BSS 尾部的自造表。需要先只读确认段尾 `0x1651F798` 起 2152 字节在运行时全零。
2. "借哪个 procId"没有结论：候选 `0x166`（TC/UB）、`0x18B`（HFR 优先级），都可能影响相机原生功能，需要逐项验证副作用。
3. 持久化：路线 G 是纯运行期数据，重启即失效；要持久还得回到磁盘补丁。

已知的结构障碍（别再去撞）：

```text
属性表要新的，但 .rodata 没有空洞
节点对象要 40 字节，但 BSS 被 52614 个符号填满
设置行是扁平列表，456 槽全满；count 在独立位置（0x1646D00C）
改 subNodes / count 对显示无效
往值选择器（音频信号）里加叶子，值非法被静默丢弃
不能动态注册新 BKID，Backup 的 ID 表是静态的
```

替代方案：用相机原生「音频信号」设置（Backup `0x01070026`）当开关。能用了，但不是"本项目的"开关。

### U-02 `priority 6` 的音效播不出来 [未解决]

## 优先级建议

如果要接着做，按这个顺序：

| 优先级 | 事项 | 理由 |
|---|---|---|
| 高 | LD_PRELOAD 正确时机验证 | 唯一可能"不碰 Sony 代码"的持久化路线，法律上更干净 |
| 高 | `priority 6` 解锁 | 直接决定像不像真快门 |
| 中 | 路线 G 只读验证 | 菜单开关的唯一可行方向 |
| 低 | 第二套音量（param `0x1002`） | 可能有额外收益，风险低，只读试探即可 |
| 低 | 其他机型特征码扫描 | 决定这套东西能不能推广 |

## 如果重来一次

```text
0. 先做只读侦察，把能读到的全部 dump 下来（maps、fd、/proc、模块文件本体）
   这一步几乎零风险，能避免 90% 的"地址错"

1. 建立 L1/L2/L3 三层验证习惯，每层都要有可观测证据

2. 优先改数据，其次改代码
   改数据只要解决"偏移语义"1 个问题；改代码要同时解决"注入、落盘、时机、安全"4 个问题

3. 任何"没反应"，先查：钩子字节在内存里吗？落盘了吗？真的重启了吗？

4. 一次只改一个变量，失败立刻回滚

5. 崩溃前先想好怎么恢复。拔电池是最可靠的恢复手段
```

操作级的细节见[逆向方法](逆向方法.md)；具体地址与结构见[相机架构](../01-固件介绍.md)和[注入机制](../教程/04-编写载荷.md)。

## G 组 · 新增音效（尝试后放弃）

### G-01 往 beeplist 的空槽位里加音效（实测无效）

- **假设**：`beeplist.txt` 决定 soundId 与文件的映射。它里面有 26 条 `None` 记录，
  表示通道存在但没挂文件。改 `None` 为自定义文件名，就能新增一个音效而不动原厂文件。
- **做法**：
  1. 把音效复制成 `/usr/share/avsystemsound/OurShutter.bin`（新增，不覆盖原厂）
  2. 改 beeplist：`BEEP_ID_MOVE_LEFT 0x000B` 的 `None` → `OurShutter.bin`
  3. 载荷 soundId 改成 `0x0B`，注入内存
  4. 重启，拍照
- **结果**：无声。分别试过改 `/tmp/beeplist.txt`（相机自己也有一份副本）和
  改 `/usr/share/avsystemsound/beeplist.txt`，都不影响播放。用同样的办法把
  CAUTION 改成指向另一个现成音效，也没有变化。
- **真相**：beeplist 不是播放时用的映射表。声音数据在启动时由别的路径加载，
  或者 RTOS 侧有独立的表。
- **代价**：两次改 beeplist + 两次重启 + 一次内存注入，约 40 分钟。
- **正确做法**：替代现有的可播槽位（priority ≤5）。30 个槽位里其实有 21 个可以安全替换，
  真正需要保留的只有对焦锁定和自拍倒计时那几个。
