# 教程 09 · 连拍支持

## 结论

一个钩子同时解决单拍和连拍。不需要两套逻辑，不需要计数，不需要状态机。

## 原因

载荷的判据是：

```
msg->type == 4  &&  msg->nid == 0x1001
```

`nid 0x1001` 是 START_EXPOSURE。真机实测它出现的次数：

| 场景 | `0x1001` 出现次数 |
|---|---|
| 单拍 1 张 | 1 |
| 连拍 8 张 | 8 |
| 连拍 5 张 | 5 |

**每帧一次，不多不少。** 所以"每收到一次就发一次播放请求"自然就对了。

不需要：

- 判断这是单拍还是连拍
- 记录已经响过几声
- 处理连拍首帧和尾帧的差异
- 任何定时器

## 演化过程

最早的单拍方案钩在 `createEvent`（fileVA `0x3C039E`，输入事件处理）。

问题：连拍不经过输入事件。按一次快门之后，后续帧是由影像核自己连发的，
Linux 侧的输入子系统完全看不到。

所以改钩 CP 收包循环。这里能看到每一帧的开始曝光通知。

改完之后单拍、连拍、10 FPS 连拍全部自动覆盖。

## 验证方法

上机测试用消息日志确认频率。**前提是先装好消息日志载荷**（见
[逆向方法](../附录/逆向方法.md) 里 `build_msglog_payload.py` 那一段），否则读到的
是空日志或者上一次的旧数据。

```bash
python tools/analysis/read_msglog.py
```

日志里能看到每次 `type=4, nid=0x1001` 的记录和时间戳。

实测数据（连拍 8 张）：

```
t=0.000  type=04  nid=1001
t=0.101  type=04  nid=1001
t=0.203  type=04  nid=1001
t=0.304  type=04  nid=1001
t=0.406  type=04  nid=1001
t=0.507  type=04  nid=1001
t=0.609  type=04  nid=1001
t=0.710  type=04  nid=1001
```

间隔约 101 ms，和 10 FPS 一致。

## 唯一的边界情况

**机械快门和电子快门都经过这个钩子。**

载荷只判断 `nid == 0x1001`，不区分快门类型。所以：

- 电子快门（静音）→ 响
- 机械快门 → 也响

如果只想在电子快门下响，需要在载荷里加判断读快门类型。这个没做。

实际使用中这不构成问题：机械快门本来就有自己的声音，多响一声反而是叠加。
但严格说，本项目没有做这个区分。

## 另一个没做的

单拍和连拍用同一个音效。如果想让单拍和连拍播不同的声音，需要改载荷，
在里面读连拍状态位。这个也没做。

当前实现是"每帧一个同样的声音"，覆盖了绝大多数使用场景。
