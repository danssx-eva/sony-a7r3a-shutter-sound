# 教程 03 · 找到触发点

## 结论

钩 `libObj.so` 的 **CP 收包循环**，fileVA `0xA31226`（模块内偏移）。

```
运行期地址 = libObj 基址 0x05DCA000 + 0xA31226 = 0x067FB226
```

## 原字节

```
7c 69 23 78
```

反汇编：

```
ldr  r4, [r7, #0x14]      ; r4 = 消息指针
ldrb r3, [r4]             ; r3 = msg->type
```

4 字节正好是两条完整的 16 位 Thumb 指令，可以整体替换后重放。

## 为什么是这个位置

### 1. 它是所有拍摄事件的汇聚点

CP（Camera Processor）收包循环处理来自影像核的所有通知。单拍、连拍、录像、结束曝光
都从这里过。钩这一个点就覆盖全部。

### 2. 消息结构可用

收到的结构是 `CpMsg`：

```
+0x00  u8   type      (0x04 = CAP_NOTIFY)
+0x01  u8
+0x02  u16  nid
+0x04  u32
+0x08  ...  payload
```

这个布局是从 21 个构造函数和 4 个处理函数的反汇编里交叉验证出来的，不是猜的。

### 3. 判据简单

```
msg->type == 4  &&  msg->nid == 0x1001
```

- `type == 4`：CAP_NOTIFY，拍摄相关通知
- `nid == 0x1001`：START_EXPOSURE，开始曝光

真机实测：

| 场景 | `nid 0x1001` 出现次数 |
|---|---|
| 单拍 1 张 | 1 |
| 连拍 8 张 | 8 |

**这就是连拍方案的核心**：不需要额外逻辑，每帧一次 `0x1001`，响应一次就对了。

## 同一循环里的其他消息

| nid | 含义 | 频率 |
|---|---|---|
| 0x1000 | CAPTURE_START | 每次拍摄会话 1 次 |
| 0x1001 | START_EXPOSURE | 每帧 1 次 ← 用这个 |
| 0x1002 | END_EXPOSURE | 每帧 1 次 |

用 `0x1002` 也能达到同样效果，但 `0x1001` 更早，声音跟快门更同步。

## 为什么不能轮询

试过定时读某个状态位判断"是否在拍"。不行：

- 轮询周期要足够短才不漏帧，但 CP 收包线程是实时优先级，加轮询会拖慢它
- 单拍时窗口只有几十毫秒，轮询很容易错过
- 相机有 177 个线程，负载本来就高（loadavg 80 上下），再叠一个轮询会明显卡

事件驱动是唯一正解。

## 钩点候选的其他位置

研究过程中试过或考虑过别的钩点，都不如这个：

| 位置 | 问题 |
|---|---|
| `createEvent`（fileVA 0x3C039E） | 输入事件，只对按键有效，拍照（尤其连拍）不经过 |
| `Bkup_Write`（fileVA 0x4062AC） | 属性写入，频率高且被多线程调用，钩了会崩 |
| `setValueToModel`（viewUnified2） | 菜单操作才调用，和拍摄无关 |

单拍方案原本用 `createEvent`，但连拍不经过那里，所以改到 CP 收包循环。

## 一句话

**钩 CP 收包循环里读 `msg->type` 的那两条指令。看一眼消息头，是"开始曝光"就响。**
